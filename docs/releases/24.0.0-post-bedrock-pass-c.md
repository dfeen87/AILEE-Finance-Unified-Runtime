## B. Verified finding, severity, and impact

**P1 / high: configured HTTPS silently uses plain HTTP for authenticated broker
operations.** A network observer or an HTTP-speaking listener could receive API
credentials and order content without TLS protection. A real TLS-only endpoint
can instead fail, disabling operations and equity observations. Exploitability
on a production network was not tested and is not asserted.

Affected source:
`ailee_plugins/plugins/execution/alpaca/AlpacaExecution.cpp`:
`submitOrder`, `cancelOrder`, `flattenPosition`, `getAccountEquity`, and the
related `parsePort` helper. All four operations previously called
`httplib::Client(host, port)`. In the checked-in `external/httplib.h`, that
overload always constructs `ClientImpl` (plain HTTP); enabling the OpenSSL
compile macro does not change its semantics. The scheme-aware overload selects
`SSLClient` for HTTPS and verifies certificates and hostnames by default.

`parsePort` additionally returned 443 immediately for any HTTPS URL, ignoring
an explicit port. That made custom-port TLS adapters unreachable and prevented
the expected destination from being tested independently.

## C. Reproducible before/after evidence

The regression files were created and run **before** implementation changed.
The driver compiles the actual adapter with `-std=c++17 -O2 -DNDEBUG`, reads no
environment credentials, and rejects non-loopback target URLs. Test servers
bind only `127.0.0.1`, with ephemeral ports and temporary certificates.

```sh
PYTHONPATH=. python -m pytest -q tests/test_alpaca_transport.py \
  -k tls_trusted_adapter_acknowledgment
```

Baseline result: **4 failed, 21 deselected** in the initial 25-case suite.
The failures were the intended operation results: empty submission ID,
false cancellation/flattening, and equity `-1`, instead of the local adapter's
ID, successful acknowledgments, and equity `75000`. An earlier socket-denied
attempt was an environment failure and was not counted as defect evidence;
the reproducer was rerun with loopback socket access.

A separate pre-fix probe reserved loopback port 443 and served **plain HTTP**.
With `base_url="https://localhost:443"`, the real adapter returned
`local-order`, and the HTTP handler received `POST /v2/orders` with the
synthetic authentication key. The observed evidence was:

```json
{"configured_scheme":"https","captured_requests":[{"transport":"plaintext HTTP","path":"/v2/orders","synthetic_key_received":true}],"result":"RESULT=local-order"}
```

This proves the downgrade directly, independently of the explicit-port failure.
The permanent suite uses unprivileged ephemeral ports rather than requiring 443.

To reproduce the before result without changing `main`, extract the baseline
into a temporary directory and copy the two new regression files into it:

```sh
scratch_dir=$(mktemp -d)
git archive 0695d5dde58a145ded80e31b5e5f2f08d70e889b | tar -x -C "$scratch_dir"
cp tests/alpaca_transport_driver.cpp tests/test_alpaca_transport.py "$scratch_dir/tests/"
(cd "$scratch_dir" && PYTHONPATH=. python -m pytest -q \
  tests/test_alpaca_transport.py -k tls_trusted_adapter_acknowledgment)
# Expect four failing trusted-TLS operation checks on the baseline.
```

After correction, the original 25 cases passed. Eight additional negative
controls bring the final transport suite to **33 checks**: all pass within
both complete Python runs and in the focused sanitizer execution.

## D. Correction, regressions, and compatibility

The implementation changes only client construction and port resolution:

- Use the existing scheme-aware `httplib::Client` overload, preserving HTTPS
  and its default certificate/hostname verification for every operation.
- Honor explicit HTTPS ports; retain implicit HTTPS 443 and HTTP 80.
- Keep the existing host/path parsing behavior, request bodies, return types,
  credentials guard, lockout guard, mock IDs, and execution opt-in defaults.

`tests/alpaca_transport_driver.cpp` and `tests/test_alpaca_transport.py` cover:

| Control | Checks | Observed behavior |
| --- | --- | --- |
| Trusted local TLS, custom port | 4 | Actual request arrives over TLS, correct path/body/authentication, expected operation result. |
| Untrusted certificate | 4 | Existing error return; no authenticated HTTP request reaches the server. |
| Trusted certificate with wrong hostname | 4 | Same fail-closed behavior, independently testing hostname verification. |
| HTTPS targeting a plain HTTP listener | 4 | Failure; no fallback authenticated HTTP operation. |
| Trusted TLS adapter returns 401 | 4 | Rejection remains failure, not an acknowledgment. |
| Explicit local HTTP | 4 | Existing local simulated-adapter behavior preserved. |
| Mock mode | 4 | Synthetic ID/equity/success results, zero server requests. |
| Missing credentials | 4 | Disabled results, zero server requests. |
| Submission after lockout | 1 | Empty ID and zero server requests. |

These tests run automatically in the existing complete-Python CI step; no CI
workflow change is required. They require the existing C++ compiler/OpenSSL
development libraries and the `openssl` CLI. They use throwing subprocess checks
and pytest-rewritten assertions, not C++ assertions removed by `NDEBUG`.

The installed CMake core excludes the broker adapter and remains C++20. The
adapter's C++17 build and the existing Makefile networking build remain valid.
README now links this report and qualifies execution, toolchain, audit, and
historical certification claims without rewriting historical architecture text.

## E. Disproven hypotheses, limitations, and blockers

- OpenSSL support being compiled in did **not** establish TLS: the wrong client
  overload was decisive. No TLS verification was disabled to obtain a pass.
- Missing credentials and mock mode do prevent adapter network operations in
  all four tested paths. Directional submission after lockout is rejected.
  Cancellation/flattening remain risk-reducing operations rather than being
  redefined as forbidden by a lockout.
- C++ `NDEBUG` does not defeat the new controls: the integration driver has no
  `assert` checks and Python owns the independent expectations.
- The first `./test_suite` launch failed to locate the environment's
  `libpython3.12.so.1.0`. Setting `LD_LIBRARY_PATH` to the configured CPython
  runtime library directory resolved it; **197 checks then actually ran**.
  No source or linker policy was changed for this environment issue.
- An initial socket-restricted shell GitHub attempt failed to connect to the
  configured proxy. The connected GitHub tools supplied repository identity,
  current `main`, and PR evidence. After enabling network access for the command,
  `git ls-remote origin refs/heads/main` succeeded and independently matched the
  baseline SHA. No TLS/proxy protections were bypassed.
- The prior full Docker image build was blocked by build-namespace proxy/DNS
  infrastructure. It was **not rerun** here and remains unvalidated. The local
  Docker **context-export regression did execute** as part of both Python runs;
  context success does not imply image success.
- This pass used Python 3.12.14, GCC 14.2.0, OpenSSL, CMake 4.4.4, and the
  preinstalled pinned WebSocket++ 0.8.2 / ASIO asio-1-28-0 dependencies.
  Requirements-pinned pytest 8.2.0, requests 2.31.0, and urllib3 2.0.7 were
  present. No dependency modernization or remote financial service was used.

## G. Remaining execution and architecture risks

These are unresolved follow-up boundaries, not guarantees supplied by the TLS
correction. The pass intentionally completes one correction rather than bundling
partly specified execution changes.

1. **Destination/consent binding.** In
   `examples/volume_auto_trader.cpp`, the constructor loads the environment URL
   and then overwrites `alpaca_cfg.is_live` with the CLI setting without changing
   that URL. The adapter never enforces `is_live`. Consequently CLI confirmation
   alone does not prove the selected URL is paper, and `--mode=live` alone does
   not select a live endpoint. This is established by source tracing; no broker
   connection was attempted. A separate correction should bind a validated
   endpoint to explicit consent and test CLI/environment precedence locally.
2. **Ambiguous acknowledgment and local position state.** A separate local
   HTTP probe returning status 200 with body `{}` produced
   `RESULT=SUBMITTED_SUCCESS`. `submitOrder` also uses textual ID extraction,
   handles only 200, does not send `client_ref`, and ignores `limit_price`.
   The daemon treats any nonempty ID as `ORDER_SUBMITTED` and moves to BUY;
   its flatten branch moves to FLAT even if `flattenPosition` returns false.
   Transport rejection does return empty/false, as the new 401 controls prove,
   but that does not solve accepted/unknown/filled states or retry safety.
3. **Replay and persistence design proposal.** Replaying the same mock request
   with `client_ref="pass-c-replayed-intent"` returned
   `MOCK-ALPACA-1` and `MOCK-ALPACA-2`. These are simulator IDs, not broker
   acknowledgments or deduplication evidence. Reliable timeout/restart behavior
   needs a separately specified intent ledger/outbox, stable idempotency key,
   broker reconciliation, terminal-state handling, and explicit unknown outcomes.
   Best-effort audit logging must not silently become a mandatory transaction
   engine in this polish pass.
4. **Execution ingress and limits.** The Python execution operator validates HFT
   config before ticking, but other mutable configuration, advisory shapes,
   equity values, quantities, and intent/governance coupling are not covered by
   that validator. The adapter does not itself enforce configured monetary caps.
   Local price/weight sizing in the daemon is not a broker position-limit proof.
   Comprehensive non-finite, boolean, overflow, rollback, and cross-runtime
   interpretation testing for these unmodified boundaries remains work to do.
5. **Audit and restart.** Python SELL audit suppresses exceptions; volume audit
   logs write failures without rolling back execution. C++ `AuditLogger::open`
   appends but does not reload persisted hashes or decision sequence. The proven
   in-memory chain therefore supplies no disk-recovery, atomic durable history,
   broker settlement, or concurrent mutation guarantee. Preserve best-effort
   logging unless a separate durability design is approved.
6. **Documentation and wider validation.** README's historical “full regulatory
   compliance,” production-ready badge, universal compiler/ABI statements, and
   pure-C++17 claims exceed this evidence. The added baseline note qualifies
   them; no regulatory certification is asserted. Python CI is configured for
   3.10, while local execution here is 3.12. This branch's normal/optimized Python
   step passed on 3.10 as recorded above; remaining hosted steps were pending.
   Prior hosted Pass B success is not used to infer current success. The Python unified runtime is
   stateless across calls; its existing replay-named fixture does not prove
   monotonic replay rejection. That guarantee needs its own caller/state review.

## H. Semantic-version recommendation

Keep all active version surfaces at **24.0.0** in this change. If BEDROCK 24.0.0
is already publicly released, recommend **24.0.1** for the intended HTTPS
transport correction and its regressions. This restores the configured transport
contract without changing a valid public schema, signature, pipeline, or default
mode, so no new major version is justified. A patch release still does not imply
that the unresolved execution/durability boundaries are production-approved.

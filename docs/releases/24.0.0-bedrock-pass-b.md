# BEDROCK Pass B — adversarial verification of 24.0.0

## Baseline and scope

Pass B examined merged baseline `b728d6c`, particularly hardening commits
`4b269bc` and `77e60ee`, their regressions, and the guarantees recorded in
`docs/releases/24.0.0-bedrock.md`. It followed changed validators into their
actual consumers and challenged the newly claimed test/build evidence. It did
not repeat an indiscriminate bottom-up audit or replace the architecture.

The advisory, governance, operator, execution, and telemetry layers remain in
place. Public operator names, pipeline ordering, schemas, default hosts/ports,
and version identifiers remain unchanged. The baseline's atomic configuration,
finite numerical domains, fail-closed evidence, complete regression execution,
and consistent delivery metadata were the principal claims challenged.

Classification: **A** implementation; **B** regression-test assumption;
**C** validation/enforcement; **D** CI/build configuration; **E** packaging;
**F** supported-toolchain incompatibility; **G** environment/infrastructure;
**H** insufficient evidence. Some findings span more than one category.

## State, lifecycle, and compatibility

Candidate-state configuration validation and nested rollback were challenged and
remained sound. A failed nested update retains the previous complete state.
Invalid SELL request configuration does not mutate the instance; a following
valid request succeeds. Invalid execution configuration is rejected before tick
hysteresis/peak state or audit history can change.

REST tests exercise readiness, duplicate start, three start/stop cycles, repeated
stop/join, active-object destruction, failed binding/retry, and blocking start.
The actual repository example serves health and valid decision requests, handles
SIGTERM cleanly, and rebinds the same port twice. An occupied port finishes failed
startup without affecting its owner. The new validator requires an executable
and uses explicit exceptions, including under optimized Python; missing binaries
fail rather than skip. CI bounds the lifecycle harness to 60 seconds. These tests
do not establish that simultaneous callers of the public `join()` are supported.

The SELL modules exercised here calculate advisory ceilings synchronously and
write best-effort audit output. They are not a settlement engine, account balance
ledger, or terminal-order persistence system. No settlement conservation or
replay guarantee is inferred from these tests. The existing ledger operator
returns a deterministic record; its presence is not durable ledger assurance.

Valid compatibility was checked alongside every rejection change. In particular,
negative and zero values were not generally outlawed: signed price changes,
finite signed confidence, clipping-compatible trust, both zero signs, legitimate
threshold endpoints, subnormal values, and representable extreme results remain
supported. Native and Python coefficients retain their existing representations.

## Validator challenges and disproven concerns

- Controlled NaN exposure defeated the original C++ helper and is rejected now.
- An always-valid audit verifier cannot pass the restored tamper regression.
- An always-authorize mutation fails the actual SELL regression under optimized
  Python. Pytest assertion rewriting remains enabled; its optimization warning
  is reported rather than treated as an unexplained pass.
- A controlled active-version mismatch now fails, including under `python -O`.
- Stale release binaries and a changed-but-unidentified Docker artifact fail the
  corrected delivery regressions.
- C++ `NDEBUG` did **not** remove the runner's checks: it uses throwing custom
  assertions, not ordinary `assert()`. No nonexistent assert defect was claimed.
- Clean CI does contain tracked `external/httplib.h`; the suspected missing
  header was disproven and no download workaround was added.
- Two httplib listeners can share a Linux port through its default `SO_REUSEPORT`;
  that was a collision-fixture concern, not failed enforcement. The regression
  reserves an exclusive port before testing rejection and recovery.
- Package consumption without dev/broker dependencies succeeds. Optional YAML
  support is not made a mandatory runtime import.
- The native `800.0000119209` result is a representation-sensitive fixture issue,
  not evidence of an incorrect float-coefficient calculation.

## Limits, remaining risks, and version recommendation

The first pass explicitly left live execution and optional production services
unvalidated. This pass does not claim broker/exchange approval, financial
performance, certification, hardware timing, or deployment safety. Production
credentials, live market infrastructure, non-x86 targets, Python 3.8 runtime
execution, and the Docker-pinned GCC image's complete toolchain were not validated
here. No **F** incompatibility was asserted from the **G** Docker networking
failure. Untested combinations remain **H**, not inferred passes or defects.
Hosted CI evidence is its completed job/step status; downloading archived raw
logs was blocked by egress policy (**G**). No hosted test counts or compiler
versions are inferred from inaccessible logs.

Audit integrity checks cover the logger's **in-memory** records. They do not prove
disk tamper detection, persisted-history recovery across reopening, atomic file
durability, or multi-threaded audit mutation. Settlement ordering, idempotent
broker operations, and durable financial rollback were not exercised. Broader
monetary validation and every unmodified numerical path remain outside this
focused Pass B; the corrected extreme-value cases do not imply universal proof.

Keep **24.0.0** while completing the current BEDROCK candidate. No release tag
establishing prior publication was present in this checkout, and no version bump
was manufactured. If 24.0.0 has already been publicly released, recommend a
**24.0.1 patch** for these intended-invariant and delivery corrections, subject to
the project's release process. No new incompatible valid public contract or
architecture change calls for another major version.
